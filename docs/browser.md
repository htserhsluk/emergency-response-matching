# Browser workflow

The public API embeds the HTML, JavaScript, CSS and Leaflet 1.9.4 assets. All business reads/writes continue through the coordinator. No credentials are sent to browser JavaScript. Forms use latitude then longitude, including zero and negative coordinates; backend validation remains authoritative.

The browser polls selected-request status and notifications every three seconds, with a ten-second delay after errors. Pending, unavailable and unmatched are distinct from assigned. Mutation retries reuse an operation key while that page remains open. After an uncertain response, retry the same unchanged action before closing/reloading; keys are currently kept in page memory. Saved request IDs may be copied and looked up after reopening.

## Map

The assistance-type filter and saved-location picker start at **All** and **All locations**. Change the type to filter saved records. Choose a single request to see it and its assigned resource, or a resource to see its eligible requests or confirmed assignment. Return to **All locations** to restore the selected type�s records. Hover for a readable label. Click a saved pin or activate it with the keyboard to open the same details dialog as the directory. The saved-location picker controls map selection. Closing details restores focus to the pin or directory row. Background refreshes preserve the selection and zoom. Click the map to select coordinates or type them directly. Blue marks a request, a teal plus marks a resource, and an amber diamond marks the selected coordinates. Use the Saved location menu to see a resource and its eligible requests numbered by distance. A check mark identifies the confirmed owner. The line is a display aid, not a route estimate. Observed distance comes from the persisted assignment intent, not browser matching. Resource coordinates are immutable and read through the coordinator. If that resource shard is unavailable, the request's saved status/distance remain available and the UI explains that coordinates are missing.

The default background is the OpenStreetMap standard tile endpoint. Its [usage policy](https://operations.osmfoundation.org/policies/tiles/) requires visible attribution, ordinary browser caching/referrers and no bulk/offline prefetch. This client requests only the displayed viewport and does not proxy, scrape or prefetch tiles. Tiles are best-effort, and requesting them reveals the viewed map area to the provider; use synthetic locations for this shared demonstration. The application works without external tiles.

`ERM_MAP_TILE_URL` and `ERM_MAP_ATTRIBUTION` on the API process configure a different permitted provider. An explicitly empty tile URL disables background tiles. The per-page `?tiles=off` switch also disables them. Keep attribution appropriate to the chosen provider. Browser configuration contains only these public values. Leaflet is served locally under its included BSD-2-Clause license; [1.9.4 reference](https://leafletjs.com/reference-1.9.4.html).

Coordinate forms, status and inbox do not depend on successful tile loading or the map library. If all JavaScript is disabled, the interactive console displays a notice; the JSON API and documented PowerShell scripts are the fallback. No server-rendered form submission path is claimed.

## Inbox

One shared local recipient (`demo`) receives an assignment notification in the same database transaction as finalization. Repeated deliveries do not create duplicate notifications. Read state is persisted on the request shard, with the same synchronous replay barrier as other mutations. The UI refreshes from the beginning on every poll so random IDs cannot hide later inserts. Cursor paging is explicit and is not a real-time event stream.

## Revised directory and location controls

The resource directory defaults to AVAILABLE and UNAVAILABLE together. Choose Available, Unavailable or Allocation history to filter on the server before pagination. Changing filters or refreshing returns to the first page; the available and unavailable views order registrations newest first. Allocation history shows the latest 50 allocations across all shards in allocation-time order. Older assignments remain accessible through lookups. Open a resource row with a click, Enter or Space to inspect its details and change availability. Close the dialog with Escape or its close button. Historical undated resources follow dated registrations. The just-created resource has its own card and lookup, so it is visible even when absent from the first directory page. Completed allocations stay in history.

Selection uses an amber diamond, request a blue R, and assigned resource a teal plus, with a legend and labels. Valid coordinate input updates selection without changing partial typing or panning on each keystroke. Use my location requests permission only when clicked; location can be approximate, poor accuracy is rejected, and manual selection remains available. Polling preserves the zoom when assignment information changes. Matching progress distinguishes active searches, retries, paused work and exhaustion within 4,000 km. Selecting an assistance type shows saved locations of that type. Selecting a resource previews up to five eligible requests and displays its confirmed assignment when available.

For a confirmed allocation the dialog groups the resource, matched request and assignment. It loads both records by ID. The request provides its description, creation time, coordinates and the saved assignment distance in metres. The resource provides its coordinates, registration time and allocation time when recorded. Older records may have only an allocation confirmation time. A failed lookup leaves the retrieved details visible and offers Retry.
